# Pyro Lua roadmap

Each milestone ends with a working, fully proven state: `gnatprove` reports zero
unproved checks and all tests pass. A milestone is done when every item in its
**Done when** list is true. Proof targets for each area are in
[PROOFS.md](PROOFS.md).

## Test infrastructure

Shared by all milestones. How tests are run, their time limits and what each commit
must add are in [STYLE.md](STYLE.md#testing).

- **Runner:** `tests/run` (every commit, 5 minute cap) and `tests/run --full` (end of
  milestone, 30 minute cap), written in Python 3 with no extra packages.
- **Reference Lua:** PUC Lua 5.4 (`brew install lua@5.4`, currently 5.4.9), used
  through explicit paths to its `lua` and `luac` binaries. Never the default `lua`,
  which is 5.5.
- **Corpus:** the official Lua 5.4 test suite (`lua-5.4.x-tests.tar.gz` from
  lua.org), downloaded by a script in `tools/` rather than committed, plus Pyro's own
  files in `tests/corpus/` (one feature or edge case per file, with intentionally
  invalid files for error cases).
- **Golden files:** expected `--tokens` / `--ast` / `--bytecode` output for the own
  corpus, regenerated deliberately and reviewed as diffs.
- **Differential runs:** the same file through Pyro and the reference, comparing the
  result.
- **Mutation fuzzing:** random mutations of corpus files fed to both Pyro and
  reference `luac -p`, comparing accept/reject. The proofs already rule out crashes;
  fuzzing finds disagreements with the reference.
- **CVE regression suite:** `tests/cve/`, one file per public PUC Lua 5.x CVE with a
  Lua-level proof of concept, each with a header giving the CVE id, the affected PUC
  versions, a one-line description and Pyro's expected behaviour. The front-end ones are
  in; runtime ones are added as M3 to M5 land (the pending list is in the suite's
  README).

## M1: Front end

Project setup, lexer, parser and resolver, all proven.

- Alire library crate `pyro_lua` (with `sparklib`) with style checks and proof settings
  in `pyro_lua.gpr`, nested crate `cli/` for the `pyrolua` executable, `.gitignore`.
- `tests/run` with stage timing, timeouts and the tag/doc checks; `tools/where`;
  the script that fetches the official Lua 5.4.9 test suite.
- `Pyro.Growable_Arrays`, `Pyro.Sources`, `Pyro.Diagnostics`, `Pyro.Symbols`.
- `Pyro.Lexer`, `Pyro.Numbers`, `Pyro.Floats` (decimal conversion only, for now).
- `Pyro.Syntax_Trees`, `Pyro.Parser`, `Pyro.Resolver`.
- Rich diagnostics (DESIGN.md, Diagnostics): the renderer, `Pyro.Graphemes` with
  tables generated by a `tools/` script at a pinned Unicode version, several errors
  per run with recovery inside intact brackets, and PUC detection points for the
  Lua-style report.
- `pyrolua --tokens`, `pyrolua --ast`, `pyrolua --check`, `pyrolua --check --lua-style`.

**Done when:**

- `gnatprove` proves everything at the M1 targets in PROOFS.md (Silver everywhere,
  Gold for growable arrays and AST well-formedness, termination of lexer and
  parser).
- For every `.lua` file in the official 5.4 test suite and the own corpus,
  `pyrolua --check --lua-style` and reference `luac -p` agree on accept/reject and, for
  rejected files, print the same message (line and text). Any remaining wording
  difference is listed in `tests/known-differences.md` with a reason, and the list is
  short.
- `tests/run --full` passes within its 30 minutes, including long mutation fuzzing
  with no accept/reject disagreement.
- Golden files exist for tokens, AST and the rich `--check` messages of the own
  corpus.
- README status and the PROOFS.md status table are updated.

## M2: Compiler and bytecode

- `Pyro.Bytecode`: Lua 5.4's instruction set (`lopcodes.h`) as typed records, prototypes,
  the ghost `Is_Valid` predicate, and an executable validator proven equal to it.
- `Pyro.Compiler`: AST to bytecode for the whole language, including closures,
  upvalues, varargs, `goto`, `<const>` constant folding, `<close>`, numeric and
  generic `for`; a faithful port of `lcode.c` and of `lparser.c`'s code generation.
- Compile-time limits (locals, upvalues, registers) with PUC Lua's errors.
- `pyrolua --bytecode`, and `pyrolua --bytecode --lua-style` in `luac -l -l`'s format.

**Done when:** every prototype the compiler returns is proven `Is_Valid` (it is checked by
the proven validator; that the validator never rejects the compiler's output is tested,
not proven); the corpus compiles; files that hit compile-time limits are rejected in
agreement with `luac -p`; golden bytecode listings exist for the own corpus; and
`pyrolua --bytecode --lua-style` matches `luac -l -l` 5.4.9 exactly on the own corpus and the
official test files: opcodes, operands, constants, slots, upvalues, locals and line
info. What cannot match (such as the addresses luac prints, which are masked) is listed
in `tests/known-differences.md` with the reason (design session).

## M3: Values, heap, tables, GC

- `Pyro.Values`, `Pyro.Heap`, `Pyro.Strings`, `Pyro.Tables`, `Pyro.Garbage_Collector`.
- Mark and sweep collector, without weak tables and finalisers.
- A random hash seed per state for strings and table keys, so scripts cannot craft keys
  that collide. The seed comes from the host through the API; the `pyrolua` program gets
  it from the operating system (a small trusted piece, added with the owner's OK).

**Done when:** `Is_Valid (Heap)`, `Is_Valid (Table)` and the GC properties are proven; unit
tests in `tests/` exercise tables (including traversal while deleting) and
collection with synthetic root sets; stress tests allocate and collect large object
graphs within the memory limit.

## M4: Virtual machine

- `Pyro.Virtual_Machine` executing compiled chunks: arithmetic, comparisons, concatenation,
  tables, closures and upvalues, varargs, metatables and all metamethods, Lua
  errors with source positions, protected calls, `<close>`.
- `Pyro.Floats` gains float formatting.
- The GC runs during execution.
- `pyrolua file.lua`, with a fixed set of host functions for testing (`print` plus
  whatever the test corpus needs: `setmetatable`, `pcall`, `error`, `type`,
  `select`, …). These live in `cli/`, not in the library.

**Done when:** the VM frame invariant is proven and the VM is Silver; a runtime
corpus of Lua scripts (written to use only the test host functions) produces
byte-identical output under Pyro and reference Lua 5.4; errors match in position and,
where practical, message.

## M5: Coroutines, weak tables, finalisers

- Coroutines as thread objects: create, resume, yield, status, wrap semantics;
  yielding across metamethods and host functions with continuations.
- Weak tables (`__mode`), finalisers (`__gc`), and the generational/incremental
  collector work if profiling shows it's needed.

**Done when:** proven at the same levels as M4, GC properties still proven with weak
references (a weakly referenced object may be collected; a strongly reachable one
may not); differential tests for coroutine and GC-related scripts pass.

## M6: Embedding API and sandbox

- The C API, `pyrolua.h`, as described in DESIGN.md: static and shared library builds, an
  example C host and a C++ example in `examples/`.
- `Pyro.Embedding`, the same API for Ada/SPARK hosts, with an example.
- Instruction budget, memory limit, depth limits.

**Done when:** the API is Silver; a script cannot exceed its limits, which is shown
by tests that run hostile scripts (infinite loops, unbounded allocation, deep
recursion, string bombs, colliding keys) through both the C and the Ada API and get
clean Lua errors; the README documents embedding.

## Later

- Performance work: profiling, instruction specialisation, table and string fast
  paths, faster collector. Proofs stay complete.
- More Gold where it pays off, for example proving the lexer against a formal token
  grammar.
- Optional companion crate implementing parts of the standard library on top of
  `Pyro.Embedding`, outside the core.
